### 2. Skills Architecture — Full 5-Layer Design (DESIGNED, NOT BUILT)
Triggered by: Pete/Marcus wanting skills revamp to match/improve on Andrew's Yggdrasil pattern, plus need for global skill management across all agent surfaces.

Reviewed Yggdrasil skills structure (Integration/Task/Meta types, YAML frontmatter, constraints-first, surface-aware tool mappings, 90-day verification). Identified WALDO's current Skill module as flat CRUD with no typing, no multi-agent support, no authorization, no performance tracking.

**5-Layer Architecture designed:**
- Layer 1: Universal Skill Registry (5 types: integration/procedural/analytical/creative/administrative, structured definitions, constraints, surface mappings, governance requirements, verification with content hash)
- Layer 2: Skill-Agent Authorization Matrix (many-to-many, 4 autonomy levels: execute_freely/execute_and_report/propose_only/disabled, conditions, expiry)
- Layer 3: Skill Execution Telemetry (per-skill execution recording, linked to sessions and data classification)
- Layer 4: Skill Performance Attribution (alignment_failure_mode: none/prompt_adequacy/agent_execution/scope_creep/tool_failure, per-skill trust decomposition)
- Layer 5: Skill Lifecycle Management (discovery of unregistered capabilities, ingestion of governed copies, distribution via bootstrap API, drift detection)

**Key design decision:** WALDO is the source of truth for all skills. External sources (Yggdrasil, Studio, M365, Azure) are authoring/execution surfaces. WALDO ingests the governed copy (Option 3). A skill does not exist in the governed ecosystem until WALDO says it does.

### 4. Gateway Redesign (DESIGNED, NOT BUILT)
Current Gateway only gates on data classification (keyword matching). Doesn't know about skills, doesn't authorize actions, routes to infrastructure targets not agents, evaluates once not continuously.

**Redesigned as two services:**
- classification_service (data sensitivity — existing, keep)
- authorization_service (skill + user + agent authorization — new)

Gateway becomes a continuous authorization evaluator, not a one-shot doorman. Checks both data classification AND skill authorization on every action.

**Key realization:** The Gateway and the MCP Server are the same thing. They merge in the build.

### 5. MCP Server — The Universal Integration Layer (DESIGNED, NOT BUILT)
Marcus discovered M365 Copilot already supports custom MCP servers (Copilot Studio, M365 Copilot, GitHub Copilot). This eliminated the native app approach as primary strategy.

**WALDO as an MCP Server exposes governance as tools:**
- waldo_authorize_skill — can I use this skill, for this user, on this data?
- waldo_get_authorized_skills — what am I allowed to do? (bootstrap)
- waldo_classify_data — what classification is this data?
- waldo_report_execution — here's what I just did (telemetry)
- waldo_check_user_clearance — is this user cleared for this action?
- waldo_get_constraints — what are the hard stops for this skill?
- waldo_report_error — structured error reporting

One MCP server URL. Every Copilot, Kindo, Kindra agent — governed.

### 6. Agent Governance Contract (DESIGNED, NOT BUILT)
Mandatory protocol block for every governed agent's system prompt:
- On startup: pull authorized skills from WALDO
- Before executing any skill: check authorization + clearance + classification
- On every user request: classify skill needed, verify agent AND user authorized
- On completion: report execution via telemetry
- On violation: deny, log, do not attempt

### 7. Telemetry Redesign (DESIGNED, NOT BUILT)
Current telemetry uses a flat payload_json blob, no event taxonomy, no session tracking, no skill connection, no structured error capture, no data lineage.

Redesigned with: TelemetrySession (groups events into user requests), TelemetryEventDetail (replaces blob with structured capture), TelemetryEventTaxonomy (controlled vocabulary), skill_id on events, parent-child event chains, data lineage tracking.

### 8. Cost Redesign (SCOPED, NOT DESIGNED)
